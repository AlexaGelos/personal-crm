# Не терять связь с людьми - как сделать

## Context

- Зачем и что меняется - в `proposal.md`, поведение - в `specs/keep-in-touch/spec.md`
- Вид экранов - макет на холсте «Личная CRM — Пора связаться»: https://claude.ai/artifact/8XqQfbVLfD3wPUKaJMwNmX. На нём 11 экранов: главная (блок свёрнут, раскрыт, после «Связались», поиск), карточка (просрочено, следующий раз, частота не задана, после «Связались»), телефон (главная, карточка, карточка после заметки). На экранах с кнопкой Play работают переключатель частоты, «Связались», «Отменить», «Показать всех» и «Свернуть». Ссылка открывается только у владельца, пока ею не поделились
- Сейчас в базе две таблицы: `contacts` (с `created_at`) и `notes` (с `contact_id`, `created_at` и индексом `notes_contact_id_idx` по этим двум полям). Заметки нельзя изменить или удалить
- Страницы рендерятся на сервере, включён `cacheComponents`: данные читаются в серверных компонентах внутри `Suspense`, текущее время в таких компонентах брать неудобно
- Даты на страницах форматируются в часовом поясе процесса Node: на сервере `TZ: Europe/Moscow` (`deploy/compose.yaml`), локально - пояс компьютера. База живёт в UTC
- Формы работают через server actions и `useActionState`, ошибки показываются текстом под формой
- Сообщение об удалении контакта (`DeletedContactNotice`) - рамка `border-mourning-line`, фон `bg-popover`, `shadow-mourning`, крестик «Закрыть», прячется через 8 секунд; пока оно на странице, атрибут `data-deleted-notice` гасит свечи
- Автотестов в проекте нет, проверка - `pnpm lint`, `pnpm build` и руками
- Тестовые контакты Данте (`pnpm db:seed:dante`) добавлены в разные дни за последние 3 года, заметки у них разбросаны по датам - на них удобно проверять просрочку руками

## Goals / Non-Goals

**Goals:**

- Срок и просрочка считаются в одном месте и одинаково для карточки и блока на главной
- Заметка и «Связались» дают одно «последнее общение», без двух источников, которые могут разойтись
- Дни считаются в том же поясе, в котором показываются даты заметок, чтобы срок совпадал с тем, что видно в карточке
- Миграция только добавляет поля: старый образ приложения работает с новой базой, откат образа не требует отката миграции

**Non-Goals:**

- Новые библиотеки, тестовый фреймворк
- Изменения тестовых данных (seed)
- История нажатий «Связались»: хранится только последнее
- Кэширование результата «Пора связаться»: данных мало, запрос дешёвый

## Decisions

### Хранение

Два новых поля в `contacts`, оба могут быть пустыми, без значения по умолчанию:

- `contact_frequency` - тип Postgres `contact_frequency` со значениями `week`, `month`, `quarter`, `year`. Пусто - «не задано»
- `last_contacted_at` - `timestamp with time zone`, момент последнего «Связались». Пусто - ни разу не нажимали

Почему так:

- Частота не числом дней: месяц, квартал и год календарные, их нельзя выразить фиксированным числом дней (31 января + месяц = 28 февраля)
- Частота не текстом с проверкой: тип Postgres даёт ту же защиту от мусора, а Drizzle выводит из него тип TypeScript
- «Связались» полем, а не заметкой: владелец решил не засорять заметки. Не отдельной таблицей отметок: для срока нужна только последняя, а для отмены хватает прежнего значения (см. «Связались» и отмена)
- Миграция генерируется `pnpm db:generate` (`drizzle/0001_...sql`): `CREATE TYPE` и два `ALTER TABLE ... ADD COLUMN` без значения по умолчанию - мгновенно, существующие строки получают пусто

### Расчёт срока - в SQL

Срок и просрочку считает база, одним выражением для карточки и блока (`src/lib/data.ts`):

- последнее общение: `coalesce(greatest((select max(created_at) from notes where contact_id = contacts.id), contacts.last_contacted_at), contacts.created_at)`. `greatest` в Postgres пропускает пустые значения, поэтому работает и без заметок, и без отметки. Подзапрос использует существующий индекс `notes_contact_id_idx`
- день последнего общения: `(last_contact_at at time zone $tz)::date`
- срок: день последнего общения + интервал по частоте (`7 days`, `1 month`, `3 months`, `1 year`), приведённый к `date`. Postgres сам подрезает конец месяца
- сегодня: `(now() at time zone $tz)::date`
- дней просрочки: `сегодня - срок`; контакт просрочен, когда это больше нуля

`$tz` - пояс процесса Node (`Intl.DateTimeFormat().resolvedOptions().timeZone`), тот же, в котором `formatDate` показывает даты. Передаётся параметром запроса.

Почему не в JavaScript: в SQL сразу работают сортировка, «первые 5» и подсчёт всех просроченных, не нужно выгружать все контакты с частотой; и не нужно брать текущее время в серверном компоненте, что неудобно с `cacheComponents`.

Дата срока для карточки возвращается текстом `YYYY-MM-DD` (`to_char`), а не объектом даты: так она не сдвинется на день из-за разницы поясов при разборе. В карточке форматируется существующим `formatDate`. Дата «Последний раз связались» - обычный момент времени, форматируется `formatDate`, как «В списке с».

### Данные для страниц

- `getContact(id)` дополнительно возвращает частоту, `last_contacted_at`, дату срока и дни просрочки. Один запрос на карточку, как сейчас
- `listOverdueContacts(limit?)` - просроченные контакты: `id`, `name`, `about`, `last_contacted_at`, дни просрочки и общее число просроченных (`count(*) over ()` в том же запросе); порядок: дни просрочки по убыванию, имя, `id`. Без `limit` - все

### «Связались» и отмена

Server actions в `src/app/actions.ts`:

- `markContacted(contactId)` - записывает `last_contacted_at = date_trunc('milliseconds', now())` и возвращает имя, прежнее значение и новое (ISO-строки). Контакта нет - «Этого контакта больше нет — возможно, его удалили». Обновляет кэш `/` и `/contacts/<id>`
- `undoContacted(contactId, previous, markedAt)` - возвращает `previous` только если сейчас в поле всё ещё `markedAt` (`where last_contacted_at = markedAt`). Если с тех пор нажали ещё раз или контакт удалили - ничего не меняет и возвращает «Отменить уже не получится». Значения проверяются схемой zod. Обновляет кэш тех же страниц

Время обрезается до миллисекунд, потому что JavaScript хранит время с точностью до миллисекунд, а Postgres - до микросекунд: без обрезки сравнение при отмене никогда бы не совпало.

Почему прежнее значение приходит с клиента, а не хранится в базе: отменить можно только 8 секунд и только из того же окна; отдельная таблица ради этого лишняя. Подделать значение может только сам владелец.

### Сообщение «Отмечено»

Клиентский компонент `ContactedNotice`: та же рамка, что у `DeletedContactNotice` (`border-mourning-line`, `bg-popover`, `shadow-mourning`), но без `data-deleted-notice` - свечи не гаснут. Иконка - горящая свеча, текст «Отмечено: <имя>», кнопка «Отменить», крестик «Закрыть», `role="status"`. Прячется через 8 секунд (как `SHOW_MS` у сообщения об удалении).

Состояние сообщения - в клиентском компоненте, а не в адресе страницы: в нём есть прежнее значение для отмены, и после обновления страницы сообщение не должно возвращаться.

### Блок на главной

Серверный компонент `KeepInTouch` (`src/components/keep-in-touch.tsx`) в своём `Suspense` между шапкой и поиском, заглушка на время загрузки - пусто (чаще всего блока нет, заглушка мигала бы зря).

- Если в адресе есть непустой `q` - ничего не показывает
- Без `?due=all` запрашивает 5 контактов, с `?due=all` - всех; общее число приходит тем же запросом
- Передаёт строки, общее число и признак раскрытия клиентскому компоненту `KeepInTouchBlock`, даже когда просроченных нет. `KeepInTouchBlock` держит сообщение «Отмечено»: если после «Связались» блок опустел, заголовка и строк нет, а сообщение остаётся на их месте, и «Отменить» возвращает блок
- Заголовок «Пора связаться» - как подпись «Заметки» в карточке: мелкие заглавные с разрядкой и линия; справа число «7 контактов» (`pluralize` с формами «контакт / контакта / контактов»)
- Строка на компьютере: аватар, имя книжным шрифтом со ссылкой на карточку, «Кто это» приглушённым цветом, «просрочено на N дней» цветом `rose`, кнопка «Связались» (контурная, 44 px высотой, обычный регистр, с галочкой)
- Строка на телефоне: имя; под ним сначала «просрочено на N дней», потом «Кто это», обрезается в одну строку именно «Кто это»; кнопка «Связались» справа, без галочки - с ней не помещается просрочка
- «Показать всех» → `?due=all`, «Свернуть» → тот же адрес без `due`. Оба через `ShowMoreButton`, который получает подпись параметром, чтобы служить и «Показать ещё». Ссылка «Показать ещё» у списка сохраняет `due`. После «Назад» из карточки блок остаётся в том виде, в каком был. Поиск, как и сейчас, оставляет в адресе только `q`, поэтому после очистки поиска блок свёрнут

### Карточка

По макету раздел о связи - отдельная полоса внизу карточки под сведениями, отделённая пунктирной линией, а не строка в списке сведений: пять кнопок частоты не помещаются в узкую колонку справа от подписи.

- Подпись «Как часто общаться» и переключатель `FrequencySwitch` (клиентский): обычная форма с пятью кнопками отправки `name="frequency"`, значения `none`, `week`, `month`, `quarter`, `year`. Выбранная - цвета главной кнопки, помечена `aria-pressed`, остальные контурные; пока сохраняется, кнопки неактивны. На компьютере кнопки в один ряд, на телефоне сеткой: «Не задано» на всю ширину, под ней четыре частоты по две в ряд
- Под переключателем строка о сроке: «Пора связаться — …» цветом `rose` с маленькой иконкой огонька или «Следующий раз — до …»
- Кнопка «Связались» с галочкой в той же полосе, есть всегда, в том числе без частоты; под ней «Последний раз связались: <дата>», если отметка есть. Сообщение «Отмечено» появляется в этой же полосе
- Ошибки переключателя и кнопки - текстом под ними, как в форме заметки

Почему переключатель не выпадающий список: два нажатия вместо одного. Почему не `ToggleGroup` из shadcn/ui: форма с кнопками работает и до загрузки JavaScript, как остальные формы приложения.

Server action `setContactFrequency(contactId, state, formData)`: проверяет значение схемой zod (`frequencySchema` в `src/lib/validation.ts`, `none` → пусто), обновляет поле, если контакта нет - возвращает «Этого контакта больше нет — возможно, его удалили». Обновляет кэш `/` и `/contacts/<id>`.

Подписи к частоте, «просрочено на N дней» и «N контактов» - в `src/lib/format.ts`, рядом с `pluralize`.

### Обновление после заметки

`addNote` сейчас обновляет только кэш карточки. Добавляем обновление `/`, чтобы при возврате на главную контакт пропал из блока. Удаление контакта уже обновляет `/`.

## Risks / Trade-offs

- [Пояс процесса и пояс показа разойдутся, если кто-то поменяет `formatDate` на явный пояс] → обе вещи берут пояс из одного места: заводим функцию `appTimeZone()` в `src/lib/format.ts` и используем её и в форматировании, и в запросах
- [«Сегодня» считается по часам базы, а не приложения] → база и приложение на одном сервере, часы общие
- [Случайное «Связались» не заметили за 8 секунд] → отметку можно перекрыть заметкой или новым «Связались» позже, но вернуть прежнее значение уже нельзя; это принято вместе с отменой на 8 секунд
- [Два быстрых нажатия «Связались» подряд] → вторая отмена вернёт значение первого нажатия, а не исходное; для отметки «связались сегодня» разницы нет
- [Блок появляется чуть позже остальной страницы и сдвигает поиск вниз] → обычно оба запроса быстрые и приходят вместе; заглушка-скелет хуже, потому что чаще всего блока нет
- [С `?due=all` при сотнях просроченных (например, если задать частоту всем контактам Данте) - длинный список] → это осознанное «Показать всех», есть «Свернуть»; для личной CRM сотни строк - нормально
- [На телефоне в строке блока мало места для «Кто это»] → «Кто это» обрезается, просрочка и кнопка видны всегда; проверяем на ширине 390 px

## Migration Plan

1. `pnpm db:generate` создаёт `drizzle/0001_*.sql`; локально применяется `pnpm db:migrate`
2. На сервере всё как обычно: merge → образ → разовый контейнер `migrate` добавляет поля → стартует новый образ → smoke `/health`
3. Откат - только вручную, запускает владелец: предыдущий образ работает с новой базой, лишние поля он не читает. Откатывать миграцию не нужно; если всё же нужно убрать поля - отдельная миграция с `DROP COLUMN` и `DROP TYPE`, частоты и отметки «Связались» при этом потеряются
