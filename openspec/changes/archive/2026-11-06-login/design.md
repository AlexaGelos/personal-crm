# Design

## Context

Зачем фича - в `proposal.md`, что должно работать - в спеках этого изменения.

Что есть сейчас:

- Next.js 16 с `cacheComponents` и `partialPrefetching`. Страница отдаётся сразу статической оболочкой, данные приходят потоком внутри `Suspense`. Кэша данных (`use cache`) в коде нет
- Весь доступ к данным - функции в `src/lib/data.ts` и `src/lib/groups.ts` и server actions в `src/app/actions.ts`. Владельца нет ни в таблицах, ни в запросах
- Образ собирается без настроек: подключение к базе создаётся при первом запросе (`src/db/index.ts`). Миграции и демо-данные - отдельные скрипты в образе, им доступны только `drizzle-orm` и `postgres`
- На сервере `deploy.sh` снимает бэкап, применяет миграции разовым контейнером, запускает новый образ. Репозиторий публичный

Что выяснилось при чтении кода Better Auth 1.7.18, последней версии на момент плана:

- Токен ссылки расходуется при первом открытии, и просроченный токен не принимается. Это даёт «работает один раз и 15 минут»
- Новая ссылка не отключает старые, лимита писем на одну почту нет. Встроенный лимит считает запросы с адреса компьютера, а не письма на почту
- При чтении сессии в Server Component Better Auth может продлить её в базе, но куку обновить не может: в Server Component куки не пишутся. Продлевать нужно там, где ответ ещё можно изменить
- Библиотека падает при запуске без секрета, поэтому создавать её можно только при первом запросе

## Goals / Non-Goals

**Goals:**

- Ни один запрос к данным нельзя написать, не указав пользователя
- У всех правил входа одна точка на сервере: обойти их запросом мимо формы нельзя
- Миграция атомарна: либо все данные получили владельца, либо база не изменилась
- Один образ на все окружения: всё читается из настроек при запуске

**Non-Goals:**

- Защита базы на уровне самого Postgres (Row Level Security)
- Лимит запросов с одного адреса и закрытая регистрация: в спеке их нет, см. Risks
- Удаление устаревших сессий по расписанию
- Правка `nginx` и `deploy.sh`: они не меняются

## Decisions

### 1. Модель данных

```
users ──< sessions          таблицы Better Auth: users, sessions, accounts, verifications
  │
  ├──< contacts ──< notes
  │        └──< contact_groups >──┐
  └──< groups ────────────────────┘

login_email_sends (email, sent_at)   журнал писем для лимита
```

- `contacts.user_id` и `groups.user_id` - `text`, обязательные, ссылаются на `users.id`. Удаления пользователя в этой фиче нет, поэтому каскада тоже нет: случайно потерять данные через него нельзя. Индексы по `user_id`
- `notes` и `contact_groups` владельца не получают: он определяется через контакт и группу
- Уникальный индекс групп становится `(user_id, lower(translate(name, 'ёЁ', 'еЕ')))`
- Таблицы во множественном числе, как уже принято в проекте (`usePlural`), идентификаторы пользователя - текстовые, какие создаёт Better Auth. Таблица `accounts` останется пустой, но она входит в стандартную схему библиотеки: убирать её ради экономии рискованно при обновлениях

### 2. Снаружи открыт один адрес Better Auth

Вместо стандартного обработчика всех путей `/api/auth/*` делаем только `GET /api/auth/magic-link/verify`. Остальное вызывается на сервере через `auth.api.*`. Обработчик сам подставляет `callbackURL=/` и `errorCallbackURL=/login/link-expired`, поэтому испорченная ссылка без параметров тоже ведёт на страницу устаревшей ссылки.

Почему: в стандартном обработчике `POST /api/auth/sign-in/magic-link` и другие пути открыты, и через них можно обойти проверку почты и лимит. Встроенный лимит с адреса компьютера отключаем (`rateLimit.enabled: false`): единственный открытый адрес принимает токен из 32 случайных символов, а при включённом лимите шестой вход за минуту из e2e получал бы ответ 429.

Отвергнуто: стандартный обработчик плюс `hooks.before` с проверками. Это работает, но оставляет снаружи пути профиля и списка сессий, которых по спеке нет.

### 3. Запрос ссылки: одна функция на все правила

`requestLoginLink(rawEmail, headers)` вызывается из server action страницы входа:

1. Привести почту к единому виду и проверить: `trim`, нижний регистр, `z.email()`
2. В транзакции с блокировкой на эту почту (`pg_advisory_xact_lock`): удалить записи журнала старше 10 минут, посчитать письма этой почты, при 3 и больше ответить «слишком часто», иначе добавить запись и удалить прежние токены этой почты из `verifications`
3. Вне транзакции вызвать `auth.api.signInMagicLink`: он создаёт новый токен и отправляет письмо

Почему журнал отдельной таблицей: строки токенов удаляются при каждом новом запросе, по ним не посчитать письма. Почему блокировка: без неё два одновременных запроса могли бы пройти лимит оба. SMTP вне транзакции: подключение к базе не держится на время отправки письма.

Неудачная отправка считается в лимит: случай редкий, а считать только успешные пришлось бы, держа блокировку на всё время отправки.

Токены хранятся в базе хэшем (`storeToken: "hashed"`): ссылку нельзя собрать из копии базы.

### 4. Сессия: единственное место продления - `src/proxy.ts`

`proxy.ts` на каждый запрос вызывает `auth.api.getSession({ headers, returnHeaders: true })` и переносит `Set-Cookie` в ответ. Поэтому срок продлевается одновременно в базе и в браузере. Настройки: `expiresIn` 30 дней, `updateAge` 1 час: запись в базу не чаще раза в час, срок считается с точностью до часа.

Все остальные места читают сессию с `disableRefresh: true`. Плагин `nextCookies` не нужен: куки ставят только обработчики маршрутов и `proxy.ts`. `cookieCache` не включаем, чтобы выход и окончание срока действовали сразу.

`proxy.ts` - первая линия защиты: без него неавторизованный пользователь успевал бы получить статическую оболочку страницы с кодом 200.

- Без входа - редирект на `/login`, кроме страниц входа
- `/login` с входом - редирект на `/`
- `POST` с заголовком `next-action` без входа пропускается: сам action проверит вход и вернёт правильный редирект. Иначе браузер получил бы HTML вместо ответа action
- Не проходят через `proxy.ts`: `_next/*`, `api/auth/*`, `health`, `icon.svg`, `opengraph-image*`, `cursors/*`, `logout`. `/api/auth/sign-in/magic-link` поэтому отвечает 404, а не редиректом
- Редиректы - относительным адресом, чтобы за `nginx` не зависеть от того, что приложение считает своим адресом

Проверка в `proxy.ts` не единственная: см. решение 5.

### 5. Доступ к данным: `userId` - обязательный первый аргумент

Все функции `data.ts` и `groups.ts` получают `userId: string` первым аргументом и фильтруют по нему. Новый модуль `src/lib/session.ts`: `getCurrentUser()` (через `cache` из React, один запрос за рендер) и `requireUserId()` (нет входа - `redirect("/login")`). Каждый server action и каждый серверный компонент с данными начинает с `requireUserId()`.

- Заметки и группы контакта фильтруются через владельца контакта и группы
- В `setContactGroups` номера групп из формы проходят через выборку `groups` с условием владельца. Новые названия ищутся только среди своих групп
- Все ответы про чужую запись совпадают с ответами про несуществующую: `CONTACT_GONE`, `GROUP_GONE`, `notFound()`
- `src/app/contacts/[id]/not-found.tsx` даёт «Контакт не найден» и для чужого, и для несуществующего контакта. Общая `src/app/not-found.tsx` остаётся для прочих адресов

Отвергнуто:

- Читать пользователя внутри функций данных. Меньше правок, но зависимость скрыта, а `tsc` не покажет забытое место
- Row Level Security в Postgres. Сильная защита, но нужна настройка на каждую транзакцию через общий пул и отдельная роль базы - слишком тяжело для этого приложения

Из-за `partialPrefetching` и скрытых, но живых страниц (React `Activity`) данные прошлого пользователя могут оставаться в памяти вкладки. Поэтому выход идёт обычной HTML-формой на `POST /logout`: это полная перезагрузка страницы, вкладка очищается целиком. Маршрут вызывает `auth.api.signOut` и отвечает `303` на `/login`. Запрос с `Sec-Fetch-Site: cross-site` отклоняется, чтобы чужой сайт не мог разлогинить пользователя.

### 6. Письма: Nodemailer и настройки

Новый модуль `src/lib/email.ts` создаёт транспорт из настроек при запуске. Настройки: `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM` (только адрес, имя «Личная CRM» добавляет код). У транспорта короткие таймауты подключения, чтобы форма не висела минутами, если почтовый сервис недоступен.

| Где              | Сервер             | Порт             | Логин и пароль |
| ---------------- | ------------------ | ---------------- | -------------- |
| Компьютер, тесты | Mailpit            | 1025, без TLS    | нет            |
| Сервер           | `smtp.resend.com`  | 465, TLS         | `resend`, ключ |

Отвергнуто: SDK Resend - спека требует одну библиотеку для всех окружений.

Письмо - HTML и текстовая версия. Цвета в HTML заданы значениями, а не токенами: почтовые программы не поддерживают переменные CSS. Это единственное исключение из правила токенов, значения собраны в одном месте.

### 7. Настройки на сервере

В `deploy/compose.yaml` в окружение приложения прямо в файле добавляются значения, которые не секрет: `BETTER_AUTH_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `EMAIL_FROM`. Так же уже сделано с `TZ`. В `.env` на сервере только три новые строки: `BETTER_AUTH_SECRET`, `SMTP_PASSWORD`, `OWNER_EMAIL`, все с проверкой `:?`. `OWNER_EMAIL` передаётся только контейнеру миграций.

Если строки нет, `docker compose` падает уже на первом шаге `deploy.sh`, с понятным сообщением и без изменений на сервере.

`getAuth()` создаёт Better Auth при первом запросе, как `db` в `src/db/index.ts`: иначе `next build` в Docker падал бы без секрета.

### 8. Миграция: одна, вручную дополненная, почта через настройку соединения

`pnpm db:generate` создаёт файл `drizzle/0003_*.sql`, затем он дополняется вручную по порядку:

1. Новые таблицы, `contacts.user_id` и `groups.user_id` без `NOT NULL`
2. Блок `DO $$`: если в `contacts` или `groups` есть строки - прочитать почту из `current_setting('app.owner_email', true)`, привести к единому виду. Почты нет - `RAISE EXCEPTION` с понятным текстом. Создать пользователя с `email_verified = true`, проставить `user_id` всем контактам и группам
3. `SET NOT NULL`, внешние ключи, новые индексы, удаление `groups_name_unique`

`src/db/migrate.ts` перед запуском миграций делает `set_config('app.owner_email', OWNER_EMAIL, false)` на своём единственном соединении (`max: 1`). Команда `pnpm db:migrate` переходит с `drizzle-kit migrate` на этот скрипт, чтобы компьютер и сервер работали одинаково.

Почему так:

- Drizzle применяет миграции в одной транзакции, поэтому всё или ничего, и `SET NOT NULL` идёт сразу после заполнения
- Почта не попадает в публичный git: это решение владельца продукта
- `email_verified = true`: почту указал сам владелец приложения. Со значением `false` Better Auth при первом входе пошёл бы по лишней ветке, которая очищает сессии и аккаунты неподтверждённого пользователя

`prepareTestDatabase` тоже передаёт почту, тестовую. В локальных тестовых базах могут лежать строки от прошлого запуска, и без этого миграция на них упала бы. Перед каждым тестом таблицы всё равно очищаются.

Отвергнуто: две миграции и скрипт заполнения между ними. Появляется промежуток, когда старая версия пишет строки без владельца, и шаг в `deploy.sh`, который надо удалять потом.

### 9. Демо-данные

`seed-tools.ts` получает `ensureOwner(db)`: найти или создать пользователя по `OWNER_EMAIL` с `email_verified = true`, без настройки - ошибка. `addContacts` проверяет, что контактов нет именно у этого пользователя. `addSeedGroups` ищет маркер, контакты и группы только у него. Новых зависимостей у скриптов нет.

### 10. Тесты

- **Настройки тестов** задаются в коде и перекрывают `.env`: `vitest.config.mts` и `playwright.config.ts` всегда указывают на Mailpit. Настоящее письмо из тестов уйти не может, даже если в `.env` указан Resend
- **Vitest:** функции данных получают `userId` прямо, таблицы очищаются как раньше, тестовый пользователь создаётся заново перед каждым тестом. В `actions.test.ts` к заглушкам `next/cache` и `next/navigation` добавляется заглушка `@/lib/session`: текущий пользователь задаётся в тесте. Для server actions - один табличный тест: каждое действие без входа не меняет базу
- **Playwright:** вход настоящий, через форму, письмо из Mailpit по HTTP API, без подмен сессии. `clearDatabase()` создаёт пользователя по умолчанию, `signIn(page, email?)` входит под ним. Лимит писем не мешает: журнал очищается вместе с таблицами
- **Время** двигается прямо в базе теста: `verifications.expires_at`, `sessions.expires_at`, `login_email_sends.sent_at`
- **Миграция:** отдельный тест на своей базе с суффиксом `_test`: применить миграции до 0002, добавить данные, применить остальные, сверить числа и связи

Сервер и скрипты выкатки автотестов не получают, по правилам проекта: сценарии «На сервере» и «Откат» проверяются настоящей выкаткой и репетицией на копии базы.

### 11. Интерфейс

- `src/app/login/page.tsx` и клиентская `src/components/login-form.tsx` по образцу `group-name-form.tsx`: `useActionState`, `noValidate`, форма работает до загрузки JavaScript
- `src/app/login/link-expired/page.tsx` на компоненте `Doorway`
- `src/components/user-menu.tsx` - серверный компонент в своём `Suspense` в шапке `layout.tsx`. Без входа не показывает ничего
- На телефоне почта обрезается многоточием, полный адрес в `title`, кнопка «Выйти» остаётся видна и не меньше 44 пикселей. Запас по ширине - не меньше 10%: в CI текст рисуется шире

### 12. Что решено без спеки

Мелочи, которые в спеке не описаны и которые легко поменять:

- После входа всегда открывается главная, а не страница, открытая до входа
- Вошедший пользователь, открывший страницу входа, попадает на главную
- Ссылка другого пользователя заменяет текущий вход в этом браузере
- Когда сработал лимит, новая ссылка не создаётся и последняя отправленная продолжает работать
- Письмо не отправилось - общая страница ошибки, как у остальных сбоев, и новых текстов нет
- У пустого списка заголовок «Пока нет ни одного контакта» остаётся, подсказка меняется на «Добавь первый контакт»
- На странице «Контакт не найден» остаётся вторая строка «Возможно, контакт удалили или в адресе опечатка.» и кнопка «К списку контактов»
- Подписи: заголовок страницы входа «Вход», поле «Почта», кнопка на странице устаревшей ссылки «На страницу входа»
- Новые тексты на «ты», как написано в спеке, хотя старые тексты приложения на «вы»

## Risks / Trade-offs

- [Почтовые сканеры и превью в мессенджерах могут открыть одноразовую ссылку раньше человека] → В спеке «открыл ссылку - я внутри», промежуточной страницы нет. Пользователь увидит «Ссылка устарела» и запросит новую. Если станет частым, отдельным изменением добавим кнопку подтверждения
- [Регистрация открыта всем, лимит только на одну почту: перебором разных адресов можно потратить дневной лимит Resend и испортить репутацию домена] → Так решено спекой, приглашений и лимита с адреса нет. Записано здесь, чтобы решение было осознанным; при злоупотреблении добавить лимит с адреса отдельным изменением
- [Удаление прежних токенов опирается на внутренний формат Better Auth: строка `verifications.value` с полем `email` и префикс `magic-link:`] → Версия закреплена в `pnpm-lock.yaml`; при обновлении библиотеки формат проверит e2e «Запросил новую ссылку»
- [Сервер может не пускать исходящие соединения на порт 465] → Проверить с сервера до merge. Есть запасной порт 2465: это правка одного значения в `deploy/compose.yaml`, код не меняется
- [`src/db/index.ts` содержит `server-only`, а `proxy.ts` собирается отдельно] → По документации Proxy работает на Node.js; это первое, что проверит первый e2e. Не заработает - вынести подключение к базе в модуль без `server-only`, смысл решения не меняется
- [Ошибка в `OWNER_EMAIL` на сервере: данные получит чужой адрес] → Перед merge сверить строку. Если ошибка случилась, данные целы: достаточно исправить почту в `users` по согласованию с владельцем или вернуться по откату
- [Лишний запрос к базе на каждый запрос к приложению] → Для нескольких друзей незаметно, индекс по токену сессии есть
- [Каждый e2e входит через форму и письмо, тесты станут медленнее примерно на 1-2 секунды на тест] → Осознанно: вход настоящий, как требует правило «e2e без моков»
- [Письмо не дошло, а новая ссылка уже отключила прежнюю] → Прежняя ссылка удаляется до отправки, поэтому такое возможно при сбое почты. Человек запрашивает ещё раз

## Migration Plan

**До merge:**

1. Показать владельцу продукта миграцию `drizzle/0003_*.sql`: она меняет существующие данные. Автовлитие включать только после согласования и шага 3
2. Репетиция на компьютере: дамп рабочей локальной базы, `pnpm db:migrate`, сверка чисел контактов, заметок, групп и связей, затем откат на копии
3. Владелец продукта: аккаунт Resend, домен `mail.crm.crmgelos.ru`, записи DNS, ключ; три строки в `.env` на сервере (сгенерировать секрет на сервере); проверка доступа сервера к `smtp.resend.com:465`
4. Записать числа контактов, заметок и групп на проде

**Выкатка** - как обычно, merge в `main`: бэкап → миграция → новый образ → smoke `/health`.

**После выкатки:** войти под своей почтой на `https://app.crmgelos.ru`, сверить числа с шагом 4, проверить сценарий двух пользователей на второй почте.

**Откат** - только вручную и только вместе, запускает владелец продукта. Порядок описан в `README.md`, раздел «Бэкапы и восстановление»: сначала `deploy.sh <SHA прошлой версии>`, затем `restore.sh` с файлом `before-deploy-…`, снятым перед выкаткой входа. Откатить только приложение нельзя: прошлая версия пишет контакты без владельца, база такую запись отклонит.
