# Личная CRM

Список людей, которых я знаю лично: кто это, откуда знакомы, телефон, почта и лента заметок о разговорах.

В приложение входят по ссылке из письма, без паролей: ввёл почту, получил письмо, открыл ссылку. Каждый видит и меняет только свои контакты.

## Как запустить

Нужны Docker Desktop, Node.js и pnpm. Все команды выполняются в папке проекта.

### База данных (PostgreSQL) и почтовая заглушка (Mailpit) в Docker

1. Если файла `.env` ещё нет, скопируйте `.env.example` в `.env` и заполните значения. Строки для входа и писем — в разделе «Вход и письма на компьютере» ниже
2. Запустить базу и заглушку: `docker compose up -d --wait`
3. Проверить, что они работают: `docker compose ps`. В колонке статуса у обоих должно быть `healthy`

Остальные команды:

- Остановить базу, данные сохранятся: `docker compose stop`
- Посмотреть логи базы: `docker compose logs db`

База доступна только с этого компьютера: `localhost:5432`. Данные хранятся в Docker-томе `personal-crm_pgdata` и не пропадают после перезапуска.

Mailpit — заглушка почтового сервиса: ловит все письма, которые отправляет приложение, и никуда их дальше не отправляет. Письма читаются на странице http://localhost:8025. Письма в заглушке пропадают при перезапуске контейнера, и это нормально: ссылка для входа живёт всего 15 минут.

### Первый запуск приложения

1. Установить зависимости: `pnpm install`
2. Создать таблицы в базе: `pnpm db:migrate`. Если в базе уже есть контакты или группы, которые появились до входа, миграция отдаёт их пользователю с почтой из строки `OWNER_EMAIL` в `.env` (при необходимости создаёт его): ни одна запись не теряется. Без `OWNER_EMAIL` на непустой базе миграция остановится с ошибкой и ничего не изменит; на пустой базе `OWNER_EMAIL` не нужна
3. По желанию — заполнить базу тестовыми данными (1000 контактов с заметками): `pnpm db:seed`. Контакты добавляются только пользователю, у которого ещё нет контактов. Заодно команда создаёт 15 групп («Работа», «Спорт», «Соседи» и другие) и раскладывает по ним тестовых контактов. Группы добавляются один раз, в том числе к уже загруженным тестовым контактам
   - Ещё 500 контактов на тему «Божественной комедии» Данте, с заметками: `pnpm db:seed:dante`. Добавляет их к уже имеющимся и ничего не меняет и не удаляет. Второй раз ничего не добавит. Заодно создаёт 25 групп и раскладывает по ним этих контактов. Часть групп — по логике поэмы («Ад», «Проводники», «Гибеллины»), часть — по тому, откуда герои родом («Флорентийцы», «Сиенцы», «Античность»). Группы добавляются один раз, в том числе к уже загруженным контактам Данте
   - Обе команды не создают пустых групп. Если группа с таким названием уже есть, команда кладёт контакты в неё и вторую такую же не создаёт
   - Тестовые данные создаются у пользователя с почтой из строки `OWNER_EMAIL` в `.env`. Если такого пользователя нет, команда его создаёт. Без `OWNER_EMAIL` команда остановится с ошибкой и ничего не добавит. Контакты и группы других пользователей команды не трогают. Чтобы увидеть тестовые данные, войдите в приложение под этой же почтой (как войти — ниже)
4. Собрать приложение: `pnpm build`
5. Запустить: `pnpm start`
6. Открыть в браузере: http://localhost:3000

Чтобы остановить приложение, нажмите `Ctrl+C` в окне, где оно запущено, или просто закройте это окно.

### Вход и письма на компьютере

В `.env` нужны такие строки (значения для компьютера):

```
BETTER_AUTH_SECRET=<случайная строка не короче 32 символов>
BETTER_AUTH_URL=http://localhost:3000
SMTP_HOST=127.0.0.1
SMTP_PORT=1025
SMTP_SECURE=false
EMAIL_FROM=noreply@localhost.test
OWNER_EMAIL=<ваша почта>
```

- `BETTER_AUTH_SECRET` подписывает вход в браузере. Случайную строку даёт команда `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`
- `BETTER_AUTH_URL` — адрес, на котором вы открываете приложение. Ссылка из письма ведёт именно на него, поэтому приложение открывайте как http://localhost:3000, а не по адресу с цифрами
- `SMTP_*` и `EMAIL_FROM` направляют письма в Mailpit. Логина и пароля у заглушки нет, строки `SMTP_USER` и `SMTP_PASSWORD` на компьютере не нужны
- `OWNER_EMAIL` — почта, которой принадлежат данные, существовавшие до входа, и тестовые данные из `pnpm db:seed`

Как войти:

1. Запустите приложение (`pnpm start` или `pnpm dev`) и откройте http://localhost:3000: покажется страница входа
2. Введите почту. На компьютере годится любая, в том числе выдуманная. Чтобы увидеть свои данные, введите почту из `OWNER_EMAIL`
3. Нажмите «Получить ссылку». Письмо не уйдёт в интернет, а окажется в заглушке
4. Откройте http://localhost:8025, письмо «Вход в Личную CRM» будет первым в списке. Нажмите в нём «Войти»: вы внутри. Ссылка работает один раз и 15 минут

Чтобы проверить, как видят друг друга двое, войдите под второй выдуманной почтой в другом браузере (или в окне инкогнито): чужих контактов там не будет.

### Повседневный запуск

1. Запустить Docker Desktop (база стартует сама)
2. `pnpm start` и открыть http://localhost:3000

После изменений в коде приложение нужно пересобрать: `pnpm build`, затем снова `pnpm start`.

### Режим разработки

`pnpm dev` — приложение на http://localhost:3000 само обновляется при изменении кода.

Если поменялась схема базы (`src/db/schema.ts`): `pnpm db:generate` создаст файл миграции в папке `drizzle/`, `pnpm db:migrate` применит его к базе.

Приложение, как и база, доступно только с этого компьютера: с телефона или другого компьютера в той же сети оно не откроется.

### Тесты

1. Запустить базу и заглушку, если они не запущены: `docker compose up -d --wait`
2. Запустить тесты: `pnpm test`

Тесты входа читают письма из Mailpit. Куда отправлять письма, тесты задают сами (`src/test/test-settings.ts`) и перекрывают `.env`: настоящее письмо из тестов не уйдёт, даже если в `.env` указан Resend. Каждый тест работает под своим пользователем и со своими адресами, чужие письма в заглушке тестам не мешают.

Тесты сами создают отдельную базу `<POSTGRES_DB>_test` (при `POSTGRES_DB=personal_crm` это `personal_crm_test`) в том же Postgres и применяют к ней миграции. Рабочая база не трогается: тесты чистят таблицы только в тестовой и отказываются запускаться, если её имя не заканчивается на `_test`. Тестовую базу можно удалить в любой момент — при следующем запуске она появится заново.

### e2e-тесты (Playwright)

Проходят главный сценарий в настоящем браузере: открыть список, добавить контакт, найти его, дописать заметку в карточке. Отдельные тесты проверяют вход по ссылке и то, что двое людей не видят данных друг друга. Входят тесты по-настоящему: просят ссылку на странице входа, берут письмо из Mailpit, открывают ссылку.

1. Один раз, после `pnpm install`, скачать браузер для тестов: `pnpm exec playwright install chromium`
2. Запустить базу и заглушку, если они не запущены: `docker compose up -d --wait`
3. Запустить тесты: `pnpm test:e2e`

Тесты сами собирают приложение (`pnpm build`) и запускают его на http://127.0.0.1:3100 — порт 3000 не занимают, так что `pnpm dev` может работать рядом. А `pnpm start` на время тестов лучше остановить: сборка заменит файлы, с которыми он работает. Приложение в тестах работает с отдельной базой `<POSTGRES_DB>_e2e_test`; её, как и базу для `pnpm test`, тесты создают и очищают сами, рабочая база не трогается. Если тест упал, в папке `test-results` лежит запись его шагов: открыть её можно командой, которую тест напишет в конце.

### Формат кода

Код оформляет Prettier. Привести весь код к единому виду: `pnpm format`. Проверить, ничего не меняя: `pnpm format:check`.

### Проверки на каждый PR (CI)

На каждый PR в `main` GitHub Actions запускает проверки (`.github/workflows/ci.yml`):

- **Lint, format, types** — `pnpm lint`, `pnpm format:check`, `pnpm typecheck`
- **Tests** — `pnpm test` и `pnpm test:e2e` на отдельной базе PostgreSQL и с почтовой заглушкой Mailpit; обе живут только на время проверки
- **Build image** — собирает образ приложения так же, как при выкатке, но никуда его не отправляет

Ветка `main` защищена: попасть в неё можно только через PR, и только когда все три проверки зелёные. Напрямую в `main` push не пройдёт. Для PR включено автовлитие: PR вливается сам, как только проверки позеленеют. Если Playwright упал, запись шагов упавшего теста лежит на странице запуска в разделе **Artifacts** (`playwright-test-results`).

## Выкатка на сервер

### Как выкатить новую версию

Влить PR в ветку `main` (напрямую в `main` push не пройдёт, см. «Проверки на каждый PR»). Дальше всё происходит само, руками ничего делать не нужно.

Что происходит после того, как PR влит (5–10 минут):

1. GitHub Actions собирает образ приложения и кладёт его в GitHub Container Registry с тегом — SHA коммита (`ghcr.io/alexagelos/personal-crm:<SHA>`)
2. Копирует всю папку `deploy/` на сервер и запускает `deploy.sh`
3. На сервере `deploy.sh` по шагам:
   - снимает бэкап базы. Если бэкап не снялся — выкатка останавливается, старая версия продолжает работать;
   - скачивает новый образ;
   - применяет миграции базы отдельным разовым контейнером. Если миграции упали — выкатка останавливается, старая версия продолжает работать;
   - запускает новую версию приложения;
   - проверяет, что `/health` отвечает 200 (приложение работает и видит базу);
   - удаляет старые образы и бэкапы: на диске остаются текущий и предыдущий образы и 30 последних бэкапов выкаток

### Как проверить

- На GitHub во вкладке **Actions** у последнего запуска «Deploy» зелёная галочка
- https://app.crmgelos.ru/health показывает `{"status":"ok"}`
- https://app.crmgelos.ru открывается страницей входа. Введите свою почту, откройте ссылку из настоящего письма: вы внутри, видны свежие изменения и ваши контакты

### Если выкатка упала

Запуск в **Actions** красный, GitHub присылает письмо. Откройте запуск и шаг «Run deploy/deploy.sh on the server»: в конце лога написано, что сломалось.

- Не снялся бэкап — новая версия не запускалась, база не менялась, на сайте осталась старая. Если в логе `required variable ... is missing a value`, в `.env` на сервере нет одной из строк для входа (см. «Что где лежит»): добавьте её и запустите выкатку заново. Другие причины: Стоит проверить место на диске (`df -h /srv`) и что база запущена (`docker ps`). Когда причина устранена, запустите выкатку заново кнопкой **Re-run jobs** на странице запуска
- Упали миграции — новая версия не запускалась, на сайте осталась старая
- Упала проверка `/health` — новая версия запущена, но не работает. Автоматически ничего не откатывается. В логе есть готовая команда отката на предыдущую версию

Откат вручную — на сервере, на любую прошлую версию. Образы текущей и предыдущей версий лежат на сервере, остальные скрипт скачает: образы публичные, как и репозиторий, секретов в них нет. SHA версии — в логе упавшей выкатки, в `deploy.log` на сервере или в списке коммитов на GitHub:

```
ssh crm
sudo -u deploy bash /srv/personal-crm/deploy.sh <SHA коммита>
```

Миграции при откате не отменяются: старая версия работает с уже обновлённой базой. Чтобы вернуть и базу, см. «Бэкапы и восстановление». Для версии, в которой появился вход, так нельзя: см. «Откат после выкатки входа».

### Бэкапы и восстановление

Каждая выкатка, в том числе ручной откат через `deploy.sh`, первым шагом снимает бэкап всей базы. Бэкапы лежат на сервере в `/srv/personal-crm/backups`, читать их может только пользователь `deploy`.

Посмотреть список (после `ssh crm`):

```
sudo -u deploy ls -l /srv/personal-crm/backups
```

Как читать имя файла:

- `before-deploy-20261105T143000Z-<SHA>.dump` — снят выкаткой 5 ноября 2026 в 14:30:00 по UTC (в Москве на 3 часа больше). `<SHA>` — версия приложения, которая стояла до выкатки: база в файле именно для этой версии. Если приложения на сервере ещё не было, вместо SHA стоит `none`. Хранятся 30 последних таких файлов. Старые удаляются только после удачной выкатки
- `before-restore-20261105T150000Z-<SHA>.dump` — копия базы, которую снял сам `restore.sh` перед восстановлением. Такие файлы сами не удаляются, лишние можно убрать руками

Бэкапы лежат на том же сервере, что и база: от порчи данных они защищают, от потери сервера — нет.

#### Откат после выкатки входа

Выкатка входа меняет данные: у каждого контакта и каждой группы появляется владелец. Прошлая версия приложения о владельце не знает, пишет контакты без него, а база такую запись отклонит. Поэтому **откатить только приложение нельзя**. Откат делается только вместе: база из копии, снятой перед выкаткой входа, и прошлая версия приложения. Запускает его человек, автоматически ничего не откатывается.

Всё, что люди успели добавить после выкатки входа, из базы пропадёт: останется только в копии `before-restore-…`, которую снимет скрипт.

Порядок, после `ssh crm`:

1. Найти копию, снятую перед выкаткой входа: `sudo -u deploy ls -l /srv/personal-crm/backups`. В её имени `before-deploy-<время>-<SHA>.dump` стоит SHA прошлой версии, той, что работала до входа. SHA прошлой версии есть и в `deploy.log` на сервере (`sudo cat /srv/personal-crm/deploy.log`)
2. Сделать с неё копию, чтобы её не удалила уборка старых бэкапов: `sudo -u deploy cp /srv/personal-crm/backups/<файл> /srv/personal-crm/backups/<файл>.keep`
3. Откатить приложение на прошлую версию: `sudo -u deploy bash /srv/personal-crm/deploy.sh <SHA прошлой версии>`
4. Вернуть базу из копии: `sudo -u deploy bash /srv/personal-crm/restore.sh /srv/personal-crm/backups/<файл>.keep`, ответить `yes`. Подробности и сообщения скрипта — в следующем разделе

Между шагами 3 и 4 прошлая версия работает с новой базой: страницы открываются, но новые контакты не сохранятся. Это недолго: сразу переходите к шагу 4.

Как проверить: `https://app.crmgelos.ru/health` показывает `{"status":"ok"}`, страницы открываются без входа, контактов, заметок и групп столько же, сколько в копии.

#### Как восстановить базу из бэкапа

Запускает только человек, на сервере (после `ssh crm`):

```
sudo -u deploy bash /srv/personal-crm/restore.sh /srv/personal-crm/backups/<имя файла>
```

Скрипт показывает, какой файл (`Backup file`) и какую базу (`Database`) заменит и какая версия приложения останется (`App version`), затем просит ввести `yes` (`Type yes to continue`). Любой другой ответ — выход, ничего не изменилось. Сообщения скрипта на английском.

После `yes` скрипт:

1. Снимает копию текущей базы: файл `before-restore-…`. Копия не снялась — выход, ничего не изменилось
2. Останавливает приложение, сайт на это время не работает
3. Удаляет базу, создаёт заново и загружает в неё бэкап
4. Запускает то же приложение той же версии и проверяет `/health`

Всё, что попало в базу после снятия бэкапа, из неё пропадёт. Останется только в копии `before-restore-…`.

**Бэкап другой версии.** Версия в имени файла может отличаться от той, что стоит сейчас (`WARNING: this backup was taken with another app version`). Обычно так и бывает: `before-deploy-…` снят при версии, которая стояла до выкатки. Скрипт версию приложения не меняет, а `/health` проверяет только связь с базой: он будет зелёным, даже если приложение ждёт более новую базу и его страницы падают. Если между версиями были миграции:

1. Сначала откатить приложение на версию из имени файла: `sudo -u deploy bash /srv/personal-crm/deploy.sh <SHA из имени>`
2. Потом запустить `restore.sh` с этим файлом. Откат сам снимет ещё один бэкап, поэтому файл для восстановления берите прежний, а не самый свежий

Если нужный файл — самый старый из 30, откат его удалит. Сначала сделайте копию с другим именем и восстанавливайте из неё: `sudo -u deploy cp <файл> <файл>.keep`.

Если миграций не было, откатывать версию не нужно.

**Если восстановление упало:**

- `FAILED: restore of …` — бэкап не загрузился, приложение остаётся выключенным, база может быть пустой. В конце лога есть готовая команда, которая вернёт базу из копии `before-restore-…`
- `FAILED: smoke after restore` — база восстановлена, но приложение не отвечает. В логе есть причина и та же команда возврата
- `Another deploy or restore is running` — сейчас идёт выкатка. Дождитесь её конца и запустите снова. Выкатка, начатая во время восстановления, упадёт с таким же сообщением: её можно запустить заново кнопкой **Re-run jobs**

Как проверить: `https://app.crmgelos.ru/health` показывает `{"status":"ok"}`, на сайте данные на момент бэкапа, `docker inspect --format '{{.Config.Image}}' prod-app-1` показывает ту же версию, что и до восстановления.

### Что где лежит

- Сервер: `ssh crm`. Выкатка заходит на сервер отдельным пользователем `deploy` (без sudo), по ключу из секрета `DEPLOY_SSH_KEY` в настройках репозитория на GitHub
- На сервере всё в `/srv/personal-crm`: файлы из папки `deploy/` (копируются при каждой выкатке, в том числе `deploy.sh` и `restore.sh`), `.env` с паролем от базы, `deploy.log` — история выкаток и восстановлений, `backups/` — бэкапы базы
- Docker compose проект `prod`: контейнеры `prod-db-1` (PostgreSQL, данные в томе `prod_pgdata`) и `prod-app-1` (приложение, слушает `127.0.0.1:3000`, снаружи — через nginx)

`.env` на сервере — права 600, владелец `deploy`. Нужны строки:

```
POSTGRES_USER=crm
POSTGRES_DB=crm
POSTGRES_PASSWORD=<длинный случайный пароль>
```

Пароль база запоминает при самом первом запуске: если потом поменять его в `.env`, приложение перестанет подключаться к базе.

Для входа нужны ещё три строки:

```
BETTER_AUTH_SECRET=<результат команды openssl rand -base64 32, сгенерируйте на сервере>
SMTP_PASSWORD=<ключ API из Resend>
OWNER_EMAIL=<почта владельца: ей достанутся контакты, которые были до входа>
```

- Без любой из них `docker compose` останавливает выкатку на первом шаге, до каких-либо изменений, и пишет, какой строки не хватает. Старая версия продолжает работать
- `BETTER_AUTH_SECRET` подписывает вход в браузере. Если его поменять, все выйдут из приложения и войдут заново; больше ничего не случится
- `OWNER_EMAIL` читает только разовый контейнер миграций. Почту проверьте внимательно перед выкаткой входа: данные получит тот, чья это почта. Строка нужна и дальше, при каждой выкатке
- Остальные настройки входа и писем (адрес приложения, сервер `smtp.resend.com`, отправитель `noreply@mail.crm.crmgelos.ru`) записаны прямо в `deploy/compose.yaml`, секретов в них нет

Письма с ссылками для входа отправляет Resend (SMTP). Что для этого нужно сделать один раз:

1. Завести аккаунт на https://resend.com и создать ключ API (права на отправку писем). Ключ — это `SMTP_PASSWORD`
2. Добавить в Resend домен `mail.crm.crmgelos.ru` и внести в DNS записи, которые Resend покажет (обычно SPF, DKIM и MX). Пока домен не подтверждён, письма не уйдут
3. Проверить, что сервер выпускает соединения на порт 465: `ssh crm`, затем `timeout 5 bash -c '</dev/tcp/smtp.resend.com/465' && echo ok`. Не открывается — порт 2465 делает то же самое; тогда замените `SMTP_PORT` на `"2465"` в `deploy/compose.yaml`

Полезные команды на сервере (после `ssh crm`):

- Состояние контейнеров: `docker ps` — у `prod-app-1` должно быть `healthy`
- Логи приложения: `docker logs --tail 100 prod-app-1`
- История выкаток: `sudo cat /srv/personal-crm/deploy.log`
- Бэкапы базы: `sudo -u deploy ls -l /srv/personal-crm/backups`
